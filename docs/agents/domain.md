# Domain docs

This is a single-context repository.

Before exploring or naming product concepts, read `CONTEXT.md`. Before changing
an architectural boundary, read the relevant files in `docs/adr/`.

Use glossary terms consistently in specs, tickets, interfaces, and tests. If a
new concept lacks a stable name, resolve it with domain modeling and update the
glossary. If proposed work contradicts an ADR, surface the conflict rather than
silently overriding it.

Create glossary entries and ADRs only when real decisions establish them;
neither location is a scratch pad or implementation plan.
